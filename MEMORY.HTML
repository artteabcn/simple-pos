Overview

A simple point-of-sale for small restaurants and shops in Thailand. Goal: a SaaS where any restaurant registers, pays a one-time fee (499 THB, plus an optional 299 THB curated-customisation add-on) and gets its own POS. Languages: Thai, English, French, German. Typical users are not technical, so plain wording and big touch targets matter more than features.

Two code bases live in this repository:

  • Legacy app (repository root): single-file Studio (index.html) that generates one static POS page per shop and commits it to GitHub. Two shops run on it (Jira-Bottega, wassanamart). Kept running untouched until cutover.
  • SaaS app (saas/): Astro + React islands + Tailwind v4 + Drizzle/D1, built to replace the legacy app.

Infrastructure

  • Hosting: Cloudflare Pages, deploys from GitHub artteabcn/simple-pos, branch main. Pages Functions in functions/ (legacy).
  • Legacy env vars (set in the Pages dashboard, as Secrets): GITHUB_TOKEN, GITHUB_REPO.
  • SaaS: deployed as a Cloudflare Worker with static assets (not Pages: @astrojs/cloudflare 14 builds dist/client + dist/server with a generated wrangler config). Worker is about 316 KB gzipped (limit 3 MiB). Config in saas/wrangler.jsonc: D1 binding DB (id filled in by Cloudflare's automatic provisioning). Secrets, names only: STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET.
  • The repository sits in OneDrive. Do not run npm there. Use saas\scripts\mirror.ps1 <install|test|build|check|dev>, which copies the source to %USERPROFILE%\_mig\simple-pos-saas and runs the script there.

Legacy app (repository root)

  • index.html: Studio. Owner sets profile and menu, presses Deploy; it commits data/<slug>-manifest.json, -menu.json and shops/<slug>.html.
  • functions/api/[[path]].js: /api/list, /api/recall, /api/deploy (unauthenticated, to be removed), /api/data (fresh read), /api/sync (merge write for bills and paid bills).

Domain rules

  • Bill maths: discount = subtotal*d%; service = (subtotal-discount)*s%; VAT 7%: included (total*7/107), added (+7%) or none. Display is whole baht.
  • Never parse a formatted amount back into a number (the string "2,400.00" parses as 2). Keep the number.
  • Records carry id and updatedAt; deletes are tombstones kept 30 days; newest updatedAt wins; caps: 30 saved bills, 500 paid bills.
  • Shop slug: letters, numbers, hyphens, 2-64 chars (used in URLs and keys). Logo URL: http(s) or site-relative only.

Going live: owner steps for the SaaS

Deployment is one GitHub Actions workflow, .github/workflows/deploy-saas.yml, modelled on Resumai's (CVarkadya/.github/workflows/deploy.yml). On a push to main that touches saas/ (or a manual run) it: type-checks and tests, creates the D1 database if missing, writes the database id, domain and email sender into wrangler.jsonc (saas/scripts/configure-wrangler.mjs), applies migrations to the remote D1, builds, deploys the Worker, creates the Stripe webhook once (its signing secret is captured and stored as a Worker secret), sets the Worker secrets, and smoke-tests /api/health and /robots.txt.

  1. Repository secrets were set on 2026-10-04 from the owner's own key files (names only here): CLOUDFLARE_ACCOUNT_ID = the Arkadyaproperties account, CLOUDFLARE_API_TOKEN = the token in CVarkadya/API keys.txt (verified: Workers, D1, Pages and the arkadya.tech zone; the "CF arkadya" token in ArkadyaApps/ADS/Cloudflare token.txt can read Workers but cannot use D1, so do not use it), STRIPE_SECRET_KEY = the live secret key of the "Thai Online Solutions" Stripe account (same account as Resumai; charges and payouts enabled), RESEND_API_KEY = the "hello" key (domain arkadya.tech is verified in Resend), APP_SECRET = freshly generated random value. To rotate any of them: gh secret set NAME -R artteabcn/simple-pos. Original instructions, if they ever need redoing: add repository secrets to artteabcn/simple-pos (Settings, Secrets and variables, Actions). GitHub cannot copy secrets from another repository, so the values must come from the owner's own files: CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID (the Arkadyaproperties account that already hosts Resumai), STRIPE_SECRET_KEY, RESEND_API_KEY, and a new random APP_SECRET (any long random string; it protects manager PINs). Names only here, never values. The Cloudflare token needs Workers, D1 and zone (custom domain) permissions in addition to what Pages needed.
  2. Optional repository variables (defaults in brackets): DOMAIN [pos.arkadya.tech], EMAIL_FROM [Simple POS <no-reply@arkadya.tech>], EMAIL_REPLY_TO [hello@arkadya.tech]. The domain is a placeholder until confirmed; it must be a hostname in a zone of the same Cloudflare account. The share image QR points at it: after changing it, re-run node design/make-og.mjs with PUBLIC_SITE_URL set and commit public/og.png.
  3. Stripe account mode. Resumai's notes say the shared Stripe account only has live keys, so every "test" payment is a real one. For a first end-to-end test, put a Stripe test secret key (sk_test_...) in STRIPE_SECRET_KEY and pay with card 4242 4242 4242 4242; the workflow creates the webhook in whichever mode the key belongs to. Switch to the live key afterwards and re-run the workflow (it creates the live-mode webhook and stores its secret). PromptPay appears at checkout only if it is enabled in the Stripe dashboard (it already is for Resumai).
  4. Merge to main (or run the workflow manually on a branch) and watch it with gh run list. The first run takes a few minutes.
  5. Try it: /en/start, pay, thank-you page, the welcome email arrives with a sign-in link, open the till, make a sale, then sign in on a second device with /en/login.

If the workflow's "Ensure D1" or "Deploy" step complains about a Cloudflare permission, the API token is missing a permission (Workers Scripts: Edit, D1: Edit, Zone/DNS for the custom domain). Claude's environments cannot reach Cloudflare or Stripe, so this workflow is the only automated path.

Database (D1, Drizzle: saas/src/db/schema.ts)

TablePurpose
shopsOne row per paying shop: slug, name, owner email, status, add-on flag, settings JSON (profile + menu) with its edit time, manager PIN hash and lockout state
customization_requestsWhat an owner asked for on the request page (needs ticked, details, contact), linked to the shop when the email matches; status new / in_progress / done. The team also gets each one by email
devicesOne row per phone or tablet that may sync a shop: hash of its own key, name, last seen, revoked at
login_linksOne-time email sign-in links (hash of the token, 15 minute expiry, used at)
manager_sessions"The PIN was entered on this device" proofs, 30 minutes, tied to the device
signupsA started checkout; holds the address for an hour; records the expected amount (49,900 or 79,800 satang)
paymentsOne row per Stripe payment; unique session id makes provisioning idempotent
stripe_eventsHandled Stripe event ids (webhooks are retried)
recordsSaved and paid bills and delete markers, keyed (shop, kind, id), with the device edit time, the server sync time and the exact numeric total

All tables carry createdAt and updatedAt. All queries live in saas/src/lib/db/; each takes the database as a parameter so tests run the real migration on Node's built-in SQLite.

SaaS (saas/src/pages/api/)

RouteWhat it does
POST /api/checkoutValidates the form, holds the address for an hour, asks Stripe for a Checkout page (THB, 499 plus optional 299), returns its URL
POST /api/stripe/webhookVerifies the Stripe signature (HMAC, 5 minute tolerance), handles each event once. A confirmed payment of the expected amount creates the shop, emails the owner a sign-in link (plus the request-page and LINE buttons if they bought the add-on) and tells the team. A full refund (charge.refunded) switches the shop off (all device keys and sign-in links) and emails the owner and the team; a partial refund only tells the team
POST /api/claimThe thank-you page trades the Stripe session id for the till key (shown once). 202 = not confirmed yet, 409 = already set up
POST /api/till/syncBearer till key. Sends changes, receives everyone else's; settings are last-edit-wins, bills merge per record; all input validated with Zod; 1 MB cap
Route (step 4)What it does
POST /api/auth/requestEmails one sign-in link per shop of that address; the answer is identical for unknown addresses; 10 links per address per hour
POST /api/auth/verifyTrades a link (token in the URL fragment, single use) for a new device key
POST /api/till/pin/unlockManager PIN check; 5 wrong tries lock it for 15 minutes on every device; returns a 30 minute proof
POST /api/till/pin/setSets or changes the PIN (4 to 6 digits); needs the proof or the current PIN once one exists
POST /api/customizationThe "tell us what you need" form: validated, saved, emailed to the team (reply goes to the customer) and confirmed to the customer with the LINE link. A hidden bot-trap field and 3 requests per address per hour
GET /api/healthSite up and database reachable (used by the deploy smoke test)

Manager PIN rule: with a PIN set, only a device holding a valid proof may change settings, menu or prices; everyone can still sell and sync bills. The PIN is stored as an HMAC with APP_SECRET, never in plain form.

Till key (now per device): 256 random bits, only its SHA-256 is stored. It lets a device sync one shop and nothing else. A device gets its key either from the thank-you page (first device) or from an emailed sign-in link. If the owner closes the thank-you page before the key is stored, claiming again replaces the unused key as long as the shop has never synced; the welcome email with a sign-in link covers the rest.

Gotchas

  • OneDrive: never install packages inside the repo (npm even replaces a junction). Use the mirror script.
  • PowerShell shows UTF-8 Thai as garbage; the files are fine. Verify with Node or a browser.
  • Dev server: run npm run dev inside the mirror folder (%USERPROFILE%\_mig\simple-pos-saas) and re-sync source with robocopy after edits. The first start takes about a minute. The Astro dev toolbar is disabled because it floats over the bottom bar and swallows taps.
  • Never read a formatted amount back into a number; payment amounts and PromptPay QR use the stored numeric total.
  • Pre-existing paid bills on the legacy app with totals of 1,000 or more were stored with the wrong total (old comma-parsing bug).
  • Pages: an SPA/static fallback answers 200 for missing files; verify live files by content-type and first bytes.
  • Production migrations and merges to main are done by the owner. A push 403 usually means the wrong GitHub account is active.

Next engineering steps

  • Cutover of the two legacy shops (Jira-Bottega, wassanamart): import their menus and paid bills into SaaS shops, then retire the legacy app. The legacy /api/deploy endpoint is unauthenticated and stays a hole until then; rebuild both shops in the legacy Studio after fix/saas-hardening is merged if they must keep running meanwhile.
  • Devices screen: list devices and switch one off (the table and revokedAt exist; there is no screen or endpoint yet). Until then a lost phone is handled by the PIN (settings stay locked) and by support revoking in D1.
  • Refund policy (built, owner to confirm): a full refund switches the till off automatically (sales are kept); a partial refund changes nothing and tells the team. To restore a shop after a mistaken refund: set shops.status back to active in D1. Resumai also listens to charge.refunded.
  • Rate limiting (optional, Cloudflare): the app already limits per address or shop (10 sign-in links per address per hour, 5 PIN tries per shop, 3 requests per address per hour, 1 hour address holds). A Cloudflare rule adds a limit per visitor address on /api/auth/request, /api/checkout, /api/customization and /api/till/pin/* so one bot cannot flood inboxes, create Stripe sessions or keep locking an owner out of their PIN. Worth adding once there is traffic; one rule is free.
  • History is capped to 500 paid bills per till and shown for 30 days; the server keeps everything. A longer history and an accountant export view are still to build. Sync returns at most 5,000 changed records per call (needs paging for very large first syncs).
  • PWA: manifest and install button for the till, and a service worker for true offline start (sales are already kept offline once the page has loaded).
  • Logo upload for receipts (needs asset storage).
